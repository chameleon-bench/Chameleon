Chameleon User Guide

Everything needed to load the benchmark into three engines and reproduce the reported ES and EM scores: dataset layout, file formats, difficulty definitions, and the evaluation protocol.

1. Overview

Chameleon is a benchmark for SQL dialect translation across MySQL, PostgreSQL, and Oracle. It contains 1,200 cross-domain databases and more than 100K execution-validated queries, partitioned into a standardized 1,000 / 100 / 100 train / dev / test split.

Every database is materialized three times, once per engine, with logically equivalent schemas and identical data. A query is written in one source dialect; translation systems must render it in a target dialect so that both queries return the same result set on their respective engines.

PropertyValue
Databases1,200 (1,000 train / 100 dev / 100 test)
Queries100K+, execution-validated
DialectsMySQL, PostgreSQL, Oracle
Translation directions6 (all ordered pairs)
Difficulty levelseasy, medium, hard, extra
MetricsExecution Success (ES), Execution Match (EM)

2. Dataset Structure

The archive unpacks into one directory per split, then one directory per database. Each database carries three dialect-specific copies of its schema and data, plus a single query file written in one source dialect. 

dataset/
├── train/                          # 1,000 databases
├── dev/                            # 100 databases
└── <db_name>/
    ├── schema/
    │   ├── <db_name>_schema_mysql.sql
    │   ├── <db_name>_schema_pg.sql
    │   └── <db_name>_schema_oracle.sql
    ├── data/
    │   ├── <db_name>_data_mysql.sql
    │   ├── <db_name>_data_pg.sql
    │   └── <db_name>_data_oracle.sql
    └── query/
        └── <db_name>_<dialect>_queries.json

The dialect suffix in the query file name identifies the source dialect of that database. A database is assigned a single source dialect during synthesis, so all its queries share the same origin. To translate into other engines, the source dialect is the one named in the file, and the remaining two are valid targets.

3. File Formats

3.1 Schema files

Plain DDL statements. Each file creates every table of one database in one engine. Column names, types, primary keys, and foreign keys are rendered in the native syntax of that engine, and the three files describe the same logical schema. 

CREATE TABLE `research_questions` (
  `question_id` INT NOT NULL COMMENT 'Unique identifier for each research question',
  `submitter_id` INT NOT NULL COMMENT 'ID of the submitter',
  `question_text` VARCHAR(255) NOT NULL,
  `submission_date` DATETIME NOT NULL,
  PRIMARY KEY (`question_id`),
  CONSTRAINT `fk_research_questions_submitter_id`
    FOREIGN KEY (`submitter_id`) REFERENCES `submitters` (`submitter_id`)
);

Primary keys are declared explicitly in every table, and primary-key values are always supplied by the data scripts rather than generated by the engine. As a result, the three engines hold identical key values and rows can be matched across engines by primary key.

3.2 Data files

One INSERT script per engine. The scripts disable foreign-key checks while loading, insert rows in a dependency-safe order, and restore the constraints afterwards. 

-- MySQL INSERT script: <db_name>
SET NAMES utf8mb4;
SET FOREIGN_KEY_CHECKS = 0;

INSERT INTO `submitters` (`submitter_id`, `submitter_name`, `email`) VALUES
  (1, 'Alice', 'alice@example.com'),
  (2, 'Bob', 'bob@example.com');
...

3.3 Query files

A JSON array. Every element is one source query with its metadata. 

[
  {
    "query_id": 1,
    "difficulty": "easy",
    "sql": "SELECT question_id, question_text FROM research_questions WHERE is_approved = 1",
    "database": "academic_research_and_evaluation",
    "dialect": "oracle"
  }
]
FieldMeaning
query_idIdentifier, unique within the database
difficultyOne of easy, medium, hard, extra
sqlSource query, executable on the source engine and returning a non-empty result
databaseDatabase name, matching the directory
dialectSource dialect: mysql, pg, or oracle

4. Benchmark Construction

Chameleon is synthesized from scratch rather than adapted from existing Text-to-SQL corpora. The construction is driven by dialect divergences: every divergence mined from transpilation engines is decomposed into concrete requirements on schemas, data values, and query patterns, so that it becomes something a database can actually exhibit and a translator can actually get wrong.

4.1 Divergence inventory

Divergences are extracted from the behaviour of widely used transpilation engines, then grouped into eight categories: keyword, function and identifier, syntax and structure, data type, numeric precision, date and time, NULL handling, and runtime semantics. Each divergence record carries the stage requirements it imposes, which is what lets the three later stages act on it rather than merely cite it.

4.2 Schema construction

A seed schema is expanded with columns whose types and constraints make the assigned divergences expressible, for example a JSON column when the divergence concerns key deletion, or a date column when it concerns format specifiers. The expanded schema is then rewritten into each engine's DDL so that the three versions describe the same logical tables, columns, keys, and constraints.

4.3 Data population

Rows are produced by simulating business operations over the schema rather than by sampling random values. The simulator also injects values that trigger the assigned divergences, because a divergence such as NULL comparison or empty-string handling only becomes visible when the data contains the right kind of value. Every insert supplies primary-key values explicitly, so all three engines end up holding the same rows under the same identifiers.

4.4 Query synthesis

Queries are generated under four inputs: the full DDL, the divergence requirements assigned to that database, a dialect knowledge base sampled per call, and column-level value statistics so that filter predicates fall inside realistic ranges. Each batch targets one difficulty level, and every generated query is executed on the source engine. Queries that fail are repaired through an execution-guided reflection loop, queries that succeed but return no rows are discarded, and only queries that execute and return a non-empty result are released.

5. Running the Synthesis

The three construction stages are exposed as command-line entry points in Chameleon-Source. They are only needed if you want to regenerate the benchmark; to use the released data, skip to Section 7.

5.1 Prerequisites

  • config/database_sync.yaml: connection settings for the MySQL, PostgreSQL, and Oracle instances
  • config/llm_config.yaml: provider, model, and API key used by all LLM calls
  • config/schema_synthesis.yaml, config/data_synthesis.yaml, config/query_synthesis.yaml: per-stage behaviour, including difficulty weights and per-call batch size

Stages must run in order. Schema expansion writes the database directories and the divergence allocation file that the later stages read.

5.2 Stage 1: schema construction

python -m schema_synthesis.schema_expander \
    --split dev \
    --databases my_database_1 my_database_2 \
    --allocate-first
OptionMeaning
--splittrain, dev, or test
--databasesProcess only the listed databases; omit to process the whole split
--limitProcess only the first N databases, useful for a trial run
--allocate-firstRun divergence allocation before expansion
--no-skipReprocess databases that were already handled

5.3 Stage 2: data population

python -m data_synthesis.synthesizer \
    --split dev \
    --db my_database_1 \
    --seed 42
OptionMeaning
--splitSplit to populate
--dbComma-separated database names; omit to process the whole split
--seedRandom seed, default 42, so a rerun reproduces the same rows
--concurrentNumber of databases processed in parallel
--allocationDivergence allocation file; defaults to the one written by stage 1
--llm-provider, --llm-modelOverride the model used for row generation
--cleanRemove existing insert scripts before regenerating

5.4 Stage 3: query synthesis

python -m query_synthesis.run \
    --dialect postgresql \
    --split dev \
    --databases my_database_1 \
    --loops-per-difficulty 1 \
    --queries-per-call 5
OptionMeaning
--dialectSource dialect of the generated queries: mysql, postgresql, or oracle
--splitSplit to synthesize for
--databasesSpace-separated database names; omit to process the whole split
--configConfig file, defaults to config/query_synthesis.yaml
--loops-per-difficultyBase number of batches per difficulty level
--queries-per-callQueries requested per LLM call

Difficulty proportions are controlled by weights in the stage config rather than by the command line, so loops-per-difficulty changes the total volume while the weight vector keeps the easy / medium / hard / extra ratio stable.

5.5 Changing the language model

Each stage reads its model from its own config file, so the three stages can use different models. The field names differ slightly between stages because each config was written independently.

StageConfig fileFields
Schema config/schema_synthesis.yaml expansion.provider, expansion.model
Data config/data_synthesis.yaml llm.provider, llm.model, llm_data_gen.temperature
Query config/query_synthesis.yaml llm.provider, llm.model, llm.temperature, llm.max_tokens
Evaluation not applicable the evaluator executes SQL and never calls a model

A provider and model must first exist in config/llm_config.yaml. To add one, append a provider block and list its models: 

providers:
  my_provider:
    name: "My Provider"
    api_key: "YOUR_API_KEY"
    base_url: "https://api.example.com/v1"
    max_n: 4
    models:
      my-model:
        name: "my-model"
        short_name: "mymodel"
        max_tokens: 32768
        temperature: 0.7
        context_window: 131072
        thinking:
          enabled: false

The key under models is the value you then write into llm.model. The thinking block controls reasoning mode for models that expose it; when a model reasons by default, disabling it is usually necessary for long query batches, because the reasoning tokens can consume the entire output budget before any SQL is emitted.

5.6 Controlling difficulty and volume

Four weights in config/query_synthesis.yaml set the target mix: 

difficulty_weights:
  easy: 0.1
  medium: 0.3
  hard: 0.4
  extra: 0.2

The weights are relative, not absolute: they are normalized, so 1 / 3 / 4 / 2 and 0.1 / 0.3 / 0.4 / 0.2 produce the same distribution. The number of batches per level is proportional to its weight, with the smallest weight yielding exactly loops_per_difficulty batches. With the default weights and loops_per_difficulty: 1, one run therefore performs 1 easy, 3 medium, 4 hard, and 2 extra batches; setting it to 2 doubles all four counts.

Volume per batch is set by queries_per_call. The expected number of queries is roughly the number of batches multiplied by this value, minus queries lost to execution failures and empty results. Two settings interact here: a large queries_per_call reduces the number of calls but makes each response longer, which raises the risk of hitting the output token limit, especially on the extra level where queries are longest.

Difficulty composition is also affected by filtering after generation. Every query is executed on the source engine; queries that error are repaired through reflection, and queries that succeed but return no rows are dropped. Since these losses are not uniform across levels, the realized distribution can drift slightly from the configured weights.

5.7 Reproducibility and cost knobs

SettingConfigEffect
seed data_synthesis.yaml, query_synthesis.yaml Fixes sampling so a rerun reproduces the same rows and query set
sample_rows query_synthesis.yaml Rows shown to the model per table; leaving it empty costs the model its data context
reflection.enabled, max_retries query_synthesis.yaml Execution-guided repair; more retries raise yield and cost
kb_reference.items_per_call query_synthesis.yaml Dialect knowledge base entries injected per call, wider sampling gives more syntactic variety
parallel.max_llm_workers, max_validation_workers query_synthesis.yaml Concurrency for generation and for execution validation
diffs_per_db, min_coverage schema_synthesis.yaml How many divergences each database receives and the minimum coverage constraint
save_raw_response query_synthesis.yaml Keeps the raw LLM response alongside each batch, useful for auditing failures

A full run over the dev split calls the model thousands of times, so cost scales with loops_per_difficulty, queries_per_call, and the number of databases. For a trial, restrict --databases to one or two entries and keep loops_per_difficulty at 1.

6. Difficulty Levels

Difficulty is defined by translation difficulty rather than structural complexity alone. A short query can be harder to translate than a long join if it hides a semantic trap, for example LOG(x), which is the natural logarithm in MySQL but the base-10 logarithm in PostgreSQL. Two factors combine: the number and type of dialect divergences a query exercises, and the structural depth at which those divergences sit.

LevelDivergencesCharacteristics
easyat most 1Simple structure, one-to-one replacement suffices
medium1 to 2Requires syntactic rewriting, but the points are independent
hard2 to 3Co-occurring divergences involving structural rewriting
extra4 or moreSemantic traps nested inside CTEs, window functions, or subqueries

Every released query has been executed on its source engine and returned a non-empty result. Queries that failed to execute, or that returned no rows, are excluded from the release because an empty result is weakly discriminative: two different queries can both return nothing.

7. Database Setup

Load the schema first, then the data, for each engine you intend to use. The commands below assume a local instance and a database named after the database directory.

MySQL

mysql -u root -p -e "CREATE DATABASE <db_name>;"
mysql -u root -p <db_name> < <db_name>_schema_mysql.sql
mysql -u root -p <db_name> < <db_name>_data_mysql.sql

PostgreSQL

createdb <db_name>
psql -U postgres -d <db_name> -f <db_name>_schema_pg.sql
psql -U postgres -d <db_name> -f <db_name>_data_pg.sql

Oracle

sqlplus system/<password>@<host>:1521/XE @<db_name>_schema_oracle.sql
sqlplus <DB_NAME>/<password>@<host>:1521/XE @<db_name>_data_oracle.sql

Because primary-key values are written explicitly in the data scripts, loading order does not affect the identifiers, and the same rows exist in all three engines after import.

8. Evaluation Protocol

Two metrics are reported. Both are computed by executing queries on real engines rather than by comparing SQL text.

  • Execution Success (ES): the fraction of translated queries that execute on the target engine without error.
  • Execution Match (EM): the fraction of translated queries whose result set equals the result set of the source query executed on the source engine.

Result comparison is order-insensitive. The evaluator normalizes each cell value, sorts the rows of both result sets by their content, and then compares row by row. Row order therefore does not affect the verdict, and a query whose output order is not fixed by an ORDER BY is judged on the set of rows it returns. The comparison is conservative: if the two engines return different row sets, the query is marked as a mismatch even when the translation itself is defensible. Errors of this kind lower a system's score rather than inflate it.

The gap between ES and EM is informative. A query can execute successfully and still return the wrong answer, for example when a function shares a name but not a meaning across dialects. That gap is where dialect-specific semantic traps appear.

9. Running the Evaluation

The evaluation toolkit lives in the Chameleon-Source repository. It takes a source query file and a translated query file, both in JSON, and writes a report. 

python -m eval.run_eval \
    --source-queries source_queries.json \
    --translated-queries translated_queries.json \
    --output eval_results.json \
    --split dev \
    --dataset-dir dataset \
    --db-config config/database_sync.yaml \
    --workers 8 \
    --query-timeout 30
OptionMeaning
--source-queriesJSON array of source queries, with the fields shown in Section 3.3
--translated-queriesJSON array of objects with query_id and translated_sql
--splittrain, dev, or test
--dataset-dirRoot of the unpacked dataset
--db-configYAML file holding MySQL, PostgreSQL, and Oracle connection settings
--workersParallel execution workers
--max-queriesEvaluate only the first N queries, useful for a quick check

The output is a JSON file with an overall report, per-difficulty and per-database breakdowns, and a results array holding the individual verdicts, including the executed target SQL and any error message. The same structure is what the leaderboard is built from.
